## 2026-05-11 — Phase 0 Slice 1: Adapt settlement + inline commitEvent

Folded per-child resolve/cancel work into a single transactional `commitEvent` driven by a new event-level settlement primitive. `commitEvent` no longer dispatches to `resolveMarket`/`cancelMarket` — it loads every child's pool + position rows in one pass, runs the pure decision function `computeEventSettlement`, and applies all balance credits, treasury moves, pool drains, market status flips, and ledger rows inside one `db.transaction`.

### New `computeEventSettlement` (`lib/settlement.ts`)
Additive — sits alongside the legacy per-child `computeSettlement` (still used by `resolveMarket`/`cancelMarket` for the integration test). Takes `{perChild: EventSettlementChildInput[]}` where each child carries its `outcome` (`resolved_yes`/`resolved_no`/`cancelled_*`), its `wpmReserve`, and a flat YES-only `positions[]` (`{userId, shares, costBasis}`). Returns per-child output bundles with `payouts`, `treasuryDelta`, `backstopAmount`, `finalStatus`, and `resolvedAs`.

Per-child semantics match PRD §Settlement:
- `resolved_yes`: holders with `shares > 0n` → `win` row of `amount = shares` (since YES shares pay 1 WPM each).
- `resolved_no`: holders with `shares > 0n` → `loss` row of `amount = 0n` (still emitted per PRD).
- `cancelled_*`: refund `costBasis` (or `zero` row if `costBasis = 0n`).

The function is pure — no DB I/O, no clock — so it'll slot into the Phase 3 settlement tests without further reshaping.

### Inlined `commitEvent` (`src/data/events.ts`)
- Opens one `db.transaction` for the whole event.
- Guards: `event_not_found` / `event_not_open` short-circuit.
- Loads `markets`/`amm_pools`/`positions` for the child set in parallel via `Promise.all`.
- Pre-flight pass classifies each child: already-resolved children get `{alreadyResolved: true}` without re-running settlement (idempotency under retry); already-cancelled likewise; missing market/pool emits an error result; remaining children feed into `settleablePlan`.
- Single call to `computeEventSettlement`.
- `applyChildSettlement` writes per-child: `balances` credits (only for `amount > 0`), `SettlePayout` rows (always, including loss/zero), `treasury` backstop or sweep with a `TreasuryBackstop` row when backstop fires, zeros `ammPools.wpmReserve`, flips `markets.status` to `resolved`/`cancelled`, and writes the `ResolveMarket`/`CancelMarket` transaction row.
- Final write flips `events.status='terminal'`.

### Legacy retention
- `resolveMarket`/`cancelMarket` in `data/markets.ts` are untouched — the integration test still calls them. `computeSettlement` (legacy single-child) is also untouched. Both go away in Phase 6 when the integration test is rewritten.
- `markets.resolvedOutcome` (A/B) is dual-written alongside `markets.resolvedAs` (yes/no) during the additive transition — A === yes under the YES-first mapping. Phase 1 drops the legacy column.

### Consumer cascade in `bet-controls.tsx`
The only consumer of either action was `src/components/bet-controls.tsx`, which had to be adjusted minimally to keep typecheck green ahead of the Phase 5 UI rewrite:
- Removed `import { sellShares } from "@/actions/sellShares"`.
- Changed `placeBet({ marketId, outcome, amount })` → `placeBet({ marketId, amount })`. The `outcome` state variable still drives display (which side is highlighted, which position is shown), but it no longer participates in the bet payload — the server always buys YES under the new model.
- Replaced `handleSell`'s body with an inline "Selling is disabled." error message so the surrounding sell-tab UI keeps compiling. The tab, related state (`sellShareAmount`, `tab`, `pickTab`), and presets are intentionally left in place — Phase 5 will remove the entire toggle/tab apparatus when it rewrites the bet form.

### Why a minimal UI patch instead of a full purge
The plan explicitly defers the A/B toggle and sell-tab removal to Phase 5 ("Bet controls / drawer: remove A/B toggle; single 'Buy YES' button per Market"). Excising the sell UI now would have rippled into `<Tabs>`/`<TabsList>`/`<TabsContent>` deletions and forced state cleanup beyond the scope of "delete the action file" — so the surgical replacement keeps the diff tight and lets the Phase 5 task own the structural redesign.

## 2026-05-11 — Phase 0 Slice 1: End-to-end smoke test

Added `tests/integration/event-flow.test.ts` exercising the full Slice 1 flow against a real Postgres database:

1. Seeds treasury + two users with starting balances.
2. Runs `binary-healthy.json` through `translateKalshiEvent` to produce the new `{event, markets[]}` shape.
3. Calls `createEvent(translation.value)` and asserts both child Markets + pools land in one transaction.
4. Bumps the child `closesAt` past `Date.now()` (fixture timestamp is in the past relative to live `placeBet`'s "betting has closed" check) and places a YES bet via the production `placeBet` on the first child.
5. Force-commits the Event with `commitEvent({eventId, perChild: [{resolved_yes}, {resolved_no}]})`.
6. Verifies: `events.status='terminal'`, both `markets.status='resolved'` with correct `resolvedAs`, winner's balance credited by exactly `shares` WPM, loser balance untouched, `SettlePayout` row emitted for the winner with `kind='win'` and `amount=shares`, one `ResolveMarket` row per child, both pools drained, and treasury grew.

### Gotchas
- The translator hardcodes the Event's `closesAt` to the fixture's `expected_expiration_time` (2026-04-25). That timestamp is in the past relative to "today" (2026-05-11), so the production `placeBet` would reject any bet against the just-created markets. The test bumps the child Markets' `closesAt` forward one hour after `createEvent` returns, before driving the bet. `commitEvent` does not consult `closesAt`, so no further patching is needed for the commit step.
- `TRUNCATE TABLE` list extended to include `events` (the existing `bet-and-resolve.test.ts` omits it; harmless there because that test never inserts events). CASCADE handles ordering automatically.
- Mocks for `@/data/auth` and `next/cache` reuse the same pattern as `bet-and-resolve.test.ts`. `vi.mock` calls are hoisted; runtime imports use top-level `await import(...)` to defer module eval until after the mocks register.

## 2026-05-11 — Phase 0 Slice 2: Author multi-outcome fixture

Added `src/lib/kalshi/fixtures/multi-outcome-healthy.json` — a 5-Market Kalshi Event modelled as the 2026 NBA Championship winner (5 candidate teams). All five child Markets share `expected_expiration_time = 2026-06-21T03:00:00Z` so the upcoming `inconsistent_close_times` gate has nothing to flag on the happy path.

Quote shapes are calibrated so the translator's per-Market checks all pass:
- Each child's `yes_ask - yes_bid = 0.02`, well under `MAX_SPREAD = 0.1`.
- Midpoints sum to ~1.0 across the field (0.30 + 0.25 + 0.20 + 0.15 + 0.10), modelling a coherent multi-outcome distribution where exactly one candidate wins. Translator does not enforce this sum — it's just realistic — so future fixtures can be skewed without breaking gates.

This fixture will drive the upcoming Slice 2 translator path (iterate `event.markets`, build N rows) and ingest test (one `events` row + 5 `markets`/`ammPools` rows).
